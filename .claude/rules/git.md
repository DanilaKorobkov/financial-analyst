# Git

## Проверки

- Нельзя пушить потенциально сломанный код - прежде чем пушить вызови `task checks` и добейся исправления ошибок.

## Типы

Закрытый список допустимых `<type>` для заголовков commit и pull request — поле `types:` в [`.github/workflows/pr-title.yml`](../../.github/workflows/pr-title.yml). Этот workflow — единственный источник правды; CI отклоняет PR с типом, которого там нет.

## Ветки

- Имя ветки: `<type>-<kebab-case>`. Никаких commits напрямую в `main`.
- Расхождение с `main` разрешаем через `git fetch origin main && git merge origin/main`.

## Staging и commits

- В индекс кладём только конкретные файлы. Никогда `git add -A` / `git add .`.
- Сообщение commit — на русском, формат `<type>: <описание>`.
- Заголовок ≤ 72 символа — посчитать перед `git commit` / `gh pr create`, не на глаз. Совпадает с лимитом из `.github/workflows/pr-title.yml`.
- Описание после `<type>:` начинается со **строчной** буквы (ru/en) и **не заканчивается точкой**. Линтер `subjectPattern: ^[a-zа-я].+(?<!\.)$` в `pr-title.yml` отклоняет «Реализовано …» / «Добавлено …» с большой буквы.
- Стиль описания — краткое страдательное причастие прошедшего времени со строчной буквы («реализовано …», «настроено …», «исправлено …»).

### Примеры

✅ хорошо:

- `feat: добавлена проверка состава индекса MOEX`
- `refactor: карточка компании собирается по секциям из двух источников`
- `fix: исправлен парсинг LISTLEVEL в карточке MOEX`

❌ плохо и как переписать:

- `feat: Добавлена проверка состава индекса MOEX` — большая буква, линтер упадёт → `feat: добавлена проверка состава индекса MOEX`.
- `refactor: переписан слой infra/moex так, чтобы карточка компании собиралась из двух независимых источников MOEX ISS` — 103 символа → `refactor: карточка компании собирается из двух источников MOEX`.
- `feat: добавлена проверка X.` — точка в конце → без точки.

То же требование применяется к **заголовку PR** — GitHub squash-merge подставляет его в commit `main`, а workflow `pull-request` гоняет тот же regex.

## Ссылки на pull request

Когда упоминаем pull request в любом виде — в ответе пользователю, в комментарии, в commit message — **всегда** прикладываем полную ссылку вида `https://github.com/<owner>/<repo>/pull/<number>`. Без неё короткая запись `PR #41` требует от пользователя дополнительно искать и кликать.

✅ хорошо:

- `PR #41 обновлён: https://github.com/DanilaKorobkov/financial-analyst/pull/41`
- `см. https://github.com/DanilaKorobkov/financial-analyst/pull/41`

❌ плохо:

- `PR #41 обновлён` — ссылки нет.
- `обновлён pull request` — ни номера, ни ссылки.

## Запрещено

- `git rebase` (включая интерактивный) — теряем линейную историю и ставим под риск чужие правки.
- `git push --force` / `--force-with-lease` — переписывает remote, ломает ревью.
- `git commit --amend` для уже запушенных commits.
- `git reset --hard` — данные пропадают безвозвратно; вместо него `git revert`, `git restore` или merge-commit.
- `git push --no-verify` — обходит хуки.

Все запреты снимаются **только** явной просьбой пользователя.
