# gRPC / proto

Конвенции `.proto`-схем проекта.

## Раскладка файлов

Один тип верхнего уровня (`message`, `service`, набор `enum`) — один
`.proto`-файл. Все файлы лежат в одной директории пакета и объявляют
общий `package` и `option go_package`.

Так proto зеркалит доменную раскладку (`internal/domain/aggregates/<X>/<file>.go`)
и страница diff'а на каждую сущность остаётся короткой.

## Doc-комментарии к message

Над каждым `message` — короткая строка о назначении сущности в
терминах домена (без упоминания провайдера или транспорта —
правило изоляции слоёв, см. `golang.md`).

## Doc-комментарии к полям

Над **каждым** полем `message` — двухстрочный комментарий:

1. **Описание** — что значит поле в домене, в каких единицах
   измеряется, что означает нулевое значение (zero — «нет данных»
   против zero — реальный 0).
2. **Пример** — последняя строка комментария вида `Пример: <value>.`
   с реальным значением по `SBER`, взятым из живого вызова
   `company.v1.CompanyService/GetCompany?ticker=SBER`. Формат значения
   совпадает с wire-форматом Connect/gRPC-JSON (числа — числа, int64
   — строка, enum — строковое имя, timestamp — ISO-8601 в UTC).

Если у `SBER` поле приходит пустым / нулевым, пример берётся с
другого репрезентативного тикера (`GAZP`, `LKOH`, `YDEX`) и в
комментарии явно проставляется тикер: `Пример (YDEX): ...`.

Шаблон:

```proto
message StockSummary {
  // Рыночная капитализация эмитента в валюте отчётности (обычно RUB),
  // в миллионах. Пример: 99990.5.
  double capital = 1;

  // Сколько лет подряд эмитент не пропускал дивидендную выплату.
  // Пример: 4.
  int64 dividend_strike = 7;
}
```

## Doc-комментарии к enum

Над `enum` — одна строка про смысл; над каждым значением (включая
`*_UNSPECIFIED`) — одна строка про то, что оно означает в домене.
Пример в enum не нужен — значения сами по себе самоописывающие.

## Doc-комментарии к service / rpc

Над `service` — одно предложение о назначении. Над каждым `rpc` —
короткое описание контракта (что принимает, что возвращает, какие
ошибки возможны по бизнес-смыслу). Запросы/ответы как отдельные
`message` документируются по общему правилу полей.
