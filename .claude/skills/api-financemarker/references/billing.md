# Тарификация `day_limit`

Primary source — официальный ответ support FinanceMarker
(`support@financemarker.ru`, переписка 2026-05-15). Цитаты ниже сохранены
дословно, чтобы будущим читателям не нужно было восстанавливать поведение
API по нашим эмпирическим тестам.

## Модель тарификации

> «Тарификация в API учитывает не сам HTTP-запрос как единичное обращение,
> а количество запрашиваемых блоков данных внутри него.»

Единица расхода `day_limit` — **блок данных (раздел)** внутри запроса, а не
HTTP-вызов. Запрос с N блоков может списать до N единиц.

## Дефолт `include` для `/stocks/{exchange}:{code}`

В письме FM сказано:

> «В запросе `Stocks` по умолчанию включены три блока: `Ratios`, `reports`,
> `dividends`.»

То же зафиксировано в swagger:

```yaml
include:
  in: query
  default: "ratios,reports,dividends"
```

⚠️ **Эмпирически runtime расходится с письмом и swagger.** Запрос
`GET /stocks/MOEX:HYDR` без `include` возвращает все массивы (`ratios`,
`reports`, `dividends` и остальные) **пустыми**, заполнен только `info`.
То есть дефолтное поведение сервера сейчас — отдавать только `info`, а не
объявленные три блока. Что именно при этом списывается, не задокументировано.

Практика: **всегда передавать `include` явно** с минимально необходимым
набором — иначе можно случайно списать единицы за блоки, которые не пришли
с данными, и наоборот, не получить ожидаемых разделов.

## Серверный кеш

> «На сервере используется кеширование. Если идентичный запрос повторяется
> в течение определённого времени и ответ возвращается из серверного кеша,
> дополнительные единицы могут не списываться.
>
> При этом кеширование зависит от конкретного набора данных и параметров
> запроса, поэтому часть повторных запросов может тарифицироваться повторно.»

Кеш существует, но **без гарантий**: один и тот же запрос может в одном
случае вернуться из кеша бесплатно, а в другом — списать единицы повторно.
TTL и условия кеширования не задокументированы. Полагаться на кеш при
проектировании клиента нельзя.

## Ключ кеша

> «Запросы с разным составом или порядком `include` рассматриваются как
> разные запросы.»

FM сравнивает строку `include` буквально:

- `include=summary,ratios` ≠ `include=ratios,summary` — разные ключи.
- `include=summary` ≠ `include=info,summary` — разные ключи, даже если
  payload идентичен (`info` возвращается всегда по умолчанию).

## Поле `day_limit` в ответе `/token_info`

В наших замерах (сессия 2026-05-14) значение `day_limit` из ответа `token_info`
стабильно возвращало одно число (`399`), тогда как реальный остаток в UI
личного кабинета параллельно двигался от `383` до `275`. В письме FM этот
момент не упомянут отдельно. Практический вывод: значение из API отстаёт
от реального остатка; для точного контроля квоты — UI личного кабинета.

## Эмпирические наблюдения, согласующиеся с моделью FM

| Тест                                                                            | Поведение                      | Объяснение                                                                                                                              |
| ------------------------------------------------------------------------------- | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| 3× повтор `include=info` на новом тикере                                        | −1 единица                     | 1 блок при первом обращении, повторы из кеша.                                                                                           |
| 3× идентичных `include=summary,ratios,dividends` на 3 новых тикерах (9 вызовов) | −18 единиц                     | 3 блока × 6 платных вызовов: кеш не сработал по всем 9 (FM явно предупреждает: повторы могут тарифицироваться).                         |
| `include=<все 10 разделов>` для нового тикера                                   | 3–5 единиц вместо ожидаемых 10 | Часть блоков (`ratios`, `reports`, `dividends`) уже находилась в кеше FM с предыдущих обращений сессии (они входят в дефолт `include`). |
| Перестановка `summary,ratios,dividends` → `dividends,ratios,summary`            | списывается повторно           | Разный порядок строки `include` = другой ключ.                                                                                          |

## Практические правила использования

- Считать стоимость запроса как «до N блоков в `include`», не как «1 за HTTP».
- Всегда передавать `include` явно с минимально необходимым набором — дефолт
  поведения runtime не совпадает с заявленным в письме FM и swagger
  (см. «Дефолт `include`» выше).
- Канонизировать строку `include` на стороне клиента: фиксированный порядок,
  единый формат, один use case → одна строка. Это максимально повышает
  вероятность попадания в серверный кеш FM (но не гарантирует).
- Не полагаться на кеш как на стратегию экономии — он недетерминирован.
  Локальный кеш на стороне Go-runtime остаётся единственным надёжным
  способом не платить за повторы.
- Поле `day_limit` из `/token_info` использовать только как приблизительный
  индикатор; точный остаток — в UI личного кабинета.
