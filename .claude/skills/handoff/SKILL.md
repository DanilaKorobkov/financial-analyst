# handoff

Скилл «передачи» работы: разработчик закончил правки и хочет довести ветку до состояния, в котором её не стыдно пушить и отдавать на ревью. Скилл прогоняет проверки, чинит ветку/коммит и пушит — но **никогда не делает push без явного `ok` от пользователя**.

## Когда запускать

Запускается **только по явной команде** пользователя (`/handoff`, «давай хэндофф», «заверши задачу», «коммить и пушь» и т.п.). Никогда не предлагать запуск самостоятельно — ни на «логическом milestone», ни в конце серии правок.

## Алгоритм

Скилл выполняется строго по шагам. Если шаг падает — останавливаемся, чиним, повторяем шаг. Не переходим дальше, пока текущий не зелёный.

### 1. Зелёные проверки

Прогнать единую команду проекта:

```bash
task check
```

Это запускает `fmt` (автофиксы форматтеров) + `lint` (все линтеры параллельно, без fail-fast). Если в проекте появятся тесты — расширяем агрегатор `check` в `Taskfile.yml`, а не дописываем шаги в скилл.

Правила:
- Не подавлять ошибки линтеров и не добавлять `// nolint` ради зелёного прогона. Чиним по существу.
- Если линтер ругается на чужой код, не относящийся к текущему диффу — фиксируем это пользователю и спрашиваем, фиксить ли в этом же коммите.
- Если правки от автофикса затронули файлы, не относящиеся к задаче — обсудить с пользователем, оставлять ли их в коммите.

### 2. Анализ диффа

```bash
git status
git diff
git diff --stat
```

Цель — понять:
- какие **логические единицы** изменений есть в working tree (одна задача? несколько независимых?);
- какие файлы относятся к каждой из них;
- нет ли мусора (отладочные `fmt.Println`, закомментированный код, временные файлы).

Если в дереве несколько независимых логических изменений — предложить пользователю **разбить на несколько коммитов** и согласовать порядок.

### 3. Имя ветки

Правила именования: `feat-<what-we-do>` в kebab-case (см. правила проекта по git).

Проверить текущую ветку:

```bash
git rev-parse --abbrev-ref HEAD
```

Сценарии:
- **`master`/`main`**: создать новую ветку `feat-<...>`, имя предложить из сути диффа, дождаться подтверждения.
  ```bash
  git switch -c feat-<name>
  ```
- **Ветка с неподходящим именем** (например, осталась с прошлой задачи или не отражает суть): предложить **переименование** и дождаться подтверждения.
  ```bash
  git branch -m feat-<new-name>
  ```
  Если ветка уже запушена — отдельно проговорить, что старое имя на remote останется висеть, и спросить, удалять ли его (`git push origin --delete <old>`).
- **Корректное `feat-<...>`-имя**: ничего не делаем.

### 4. Сообщение коммита

Формат:

```
<type>: <короткое описание в нижнем регистре>

<опциональное тело: что и зачем; ссылки на тикеты/обсуждения>
```

Типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `ci`.

Правила:
- Заголовок ≤ 72 символов, в повелительном наклонении («add», «fix», «убрать»).
- Тело — только если действительно объясняет «почему». Не пересказывать дифф.
- Никаких авто-приписок «Co-Authored-By» / «Generated with» — отключено глобально в `~/.claude/settings.json`.
- Сообщение коммита пишем **на русском языке** (заголовок и тело).

### 5. Подтверждение перед коммитом

**Блокирующий шаг.** Показать пользователю единым сообщением:

1. Список файлов, которые пойдут в коммит (по делу, без шума).
2. Предложенное сообщение коммита (заголовок + тело).
3. Имя ветки (если меняли — подсветить старое → новое).

Дождаться `ok` или правок. **Не коммитить и не пушить** до явного подтверждения. Если пользователь правит сообщение/имя ветки — повторить показ и снова дождаться `ok`.

### 6. Коммит и push

После `ok`:

```bash
git add <конкретные файлы>          # никогда git add -A / git add .
git commit -m "<заголовок>" -m "<тело>"   # тело — опционально
git push -u origin feat-<name>      # -u при первом пуше ветки
```

Запреты:
- `--no-verify`, `--amend`, `push --force` — только если пользователь явно попросил.
- Никогда не коммитить файлы, похожие на секреты (`.env`, `*.key`, `credentials.*`). Если такие попали в дифф — остановиться и предупредить пользователя.

### 7. Создание PR

После успешного push скилл **сам** создаёт pull request — отдельной просьбы не требуется.

Алгоритм:

1. Проверить, есть ли уже открытый PR для текущей ветки:
   ```bash
   gh pr view --json number,url,state 2>/dev/null
   ```
   - Если PR уже открыт — просто показать ссылку и закончить. Ничего не пересоздавать.

2. Если PR нет — собрать **название** и **описание** на основе диффа `main..HEAD` и истории коммитов ветки:

   - **Название PR:** короткое, в нижнем регистре, отражает суть всех коммитов ветки (не только последнего). Если в ветке один коммит — обычно совпадает с заголовком коммита.
   - **Описание PR:** структура
     ```
     ## Что сделано
     - <маркированный список ключевых изменений по смысловым группам>

     ## Зачем
     <1–3 предложения про мотивацию: какую задачу/проблему решаем>

     ## Как проверить
     - <команды/шаги, которыми ревьюер может убедиться, что всё работает: `task check`, ручные сценарии и т.п.>
     ```
     Секции, в которых нечего написать, опускаем целиком — не оставляем пустых заголовков.

3. Показать пользователю **предложенное название и описание PR** единым сообщением и дождаться `ok` или правок (блокирующий шаг — как и подтверждение коммита).

4. После `ok` создать PR:
   ```bash
   gh pr create \
     --base main \
     --head <текущая ветка> \
     --title "<название>" \
     --body "<описание>"
   ```
   Базовая ветка по умолчанию — `main` (или иная default-ветка проекта, если она другая — определять через `gh repo view --json defaultBranchRef`).

5. Показать ссылку на созданный PR.

**Язык PR:** название и описание пишутся **на русском языке**.

## Что скилл делать НЕ должен

- Запускать `master` / `main` push.
- Мерджить PR — мердж делает человек.
- Делить большие изменения на «искусственно мелкие» коммиты ради дробления — группируем по смыслу.
- Молча править чужие места (вне диффа) даже если линтер ругается — всегда сначала согласовать.
- Создавать PR без явного `ok` пользователя на предложенные название и описание.
