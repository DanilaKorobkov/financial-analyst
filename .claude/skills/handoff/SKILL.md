## 1. Синхронизация с main

Обновляем локальный `main` и подмёрживаем в текущую ветку:

```bash
git fetch origin main
git merge origin/main
```

При конфликтах — разрешаем их вручную и завершаем merge-commit (без `rebase`, см. `.claude/rules/git.md`).

## 2. Проверки

Вызываем **task fmt checks** и устраняем все issues шаг за шагом.

## 3. Формируем название ветки

Смотрим все изменения сделанные в этой ветке с момента ее создания и чем она отличается от текущего main
`git diff main...HEAD`, анализируем и понимаем, что конкретно изменилось.
Переименовываем текущую ветку в соответствии с тем, что реально изменилось в diff
Если мы были на ветке `main` - создаем новую ветку.

Название передаем на валидацию пользователю в формате: Ветка: old-name → new-name

## 4. Commit & Push

Формируем название и описание commit самостоятельно и сразу делаем commit & push — подтверждение пользователя не требуется.

Описание — концептуальное: коротко о сути и зачем, без перечисления конкретных файлов, функций и технических деталей. Пользователь, прочитав описание, сам решит, нужно ли ему смотреть diff.

Пример:

```text
Название commit: краткий заголовок

Описание commit:
## Что сделано
Одно-два предложения о сути изменения.

## Зачем
Одно предложение о мотиве.
```

## 5. Pull requests

Раз вызван `handoff` — PR создаётся (или актуализируется) без отдельного подтверждения.

Описание — такое же концептуальное, как у commit: суть и мотив, без технических подробностей и списков затронутых файлов/функций.

### Если открытого pull request ещё нет

Формируем название и описание и создаём PR:

```text
Название pull request: краткий заголовок

Описание pull request:
## Что сделано
Одно-два предложения о сути.

## Зачем
Одно предложение о мотиве.
```

### Если открытый pull request уже есть

Актуализируем его название и описание по тому же формату.

## Запреты skill

- merge PR (это делает человек)
- править файлы вне diff без согласования
- уходить в технические детали в описаниях commit/PR
